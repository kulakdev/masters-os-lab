# Лабораторна робота №2 — Порівняльний аналіз методів міжпроцесної взаємодії (IPC)

## 1. Мета роботи

Дослідити та порівняти різні механізми міжпроцесної взаємодії POSIX за трьома
параметрами: **затримка (latency)**, **пропускна здатність (throughput)** та
**ємність каналу (capacity)**. Результат — робочі демонстраційні програми мовою C
та порівняльна таблиця з висновками.

## 2. Досліджувані механізми

| # | Метод (CLI) | Реалізація |
|---|-------------|------------|
| 1 | `mmap_file` | `open()` + `ftruncate()` + `mmap(MAP_SHARED)` на звичайному файлі |
| 2 | `mmap_anon` | `mmap(MAP_SHARED\|MAP_ANONYMOUS)` — спільна пам'ять після `fork()` |
| 3 | `shm` | POSIX `shm_open()` + `mmap(MAP_SHARED)` |
| 4 | `file` | `open()`/`pwrite()`/`pread()` + опитування розміру через `fstat()`; окремий режим `--fsync` |
| 5 | `pipe` | анонімний `pipe()` |
| 6 | `fifo` | іменований канал `mkfifo()` |
| 7 | `socket` | `socketpair(AF_UNIX, SOCK_STREAM)` |
| 8 | `mqueue` | POSIX черга повідомлень `mq_open()`/`mq_send()`/`mq_receive()` (лише Linux) |

Спільна пам'ять (методи 1–3) реалізована як **кільцевий буфер на 64 слоти** з
атомарними лічильниками `head`/`tail` (C11 `<stdatomic.h>`, `memory_order_acquire/release`),
кожен лічильник вирівняний на окрему кеш-лінію 128 байт (захист від false sharing).
Затримка вимірюється тим самим відображенням через протокол ping-pong `seq`/`ack`.

## 3. Методика вимірювань

- **Harness:** єдиний бінарний файл `ipc_benchmark`, `fork()`: батько — producer,
  дитина — consumer; час знімається `clock_gettime(CLOCK_MONOTONIC)`.
- **Throughput:** producer передає `N` повідомлень розміру `S`; тривалість — від
  першого запису до отримання останнього повідомлення consumer-ом (`waitpid`);
  результат — `MB/s` (корисне навантаження) та `msgs/s`.
- **Latency:** `N` циклів «запит → відлуння»; наведено **односторонню** затримку
  `RTT/2` у µs.
- **Capacity:** неблокуюче заповнення каналу до `EAGAIN` (pipe/fifo/socket/mqueue),
  для mmap/shm — ємність кільцевого буфера, для file — вільне місце ФС (`statvfs`).
- Кожна конфігурація виконана **3 рази**, у таблицях — **медіана**.
- Розміри payload: **64 B** (latency-bound), **4 KiB** (page-size), **64 KiB**
  (bandwidth-bound). mqueue обмежена ядром `msgsize_max = 8192 B`, тому 64 KiB
  для неї неможливий.

## 8. Висновки

1. **Спільна пам'ять — безумовний лідер за латентністю та піковою пропускною
   здатністю.** У стаціонарному режимі немає системних викликів на кожне
   повідомлення: після початкового `mmap` процеси лише читають/пишуть пам'ять і
   синхронізуються атомарними операціями. Затримка ~0.07–0.11 µs — у 50–150 разів
   менше, ніж у `pipe`/`socket`/`mqueue`, де кожна передача — це мінімум два
   системних виклики та два перемикання контексту. Пропускна здатність сягає
   десятків GB/s (обмежена пам'яттю та узгодженістю кешів, а не ядром).

2. **Три режими mmap практично еквівалентні за швидкістю, але різняться за
   призначенням:**
   - `mmap_anon` — найпростіший у налаштуванні (без файлу й імені), але працює
     лише між спорідненими процесами після `fork()`;
   - `mmap_file` — додає `open()`+`ftruncate()` при створенні (разова ціна), дані
     проходять через page cache; зручний, коли потрібна персистентність;
   - `shm_open` — іменований сегмент у `dev/shm`, доступний **незалежним**
     процесам; потребує явного `shm_unlink()`, інакше сегмент «протікає».
   Різниця в цифрах (0.07…0.11 µs) лежить у межах шуму планувальника.

3. **`pipe` і `fifo` — один і той самий механізм ядра.** Різниця лише в тому, що
   FIFO має ім'я у файловій системі (і повільніший `open()` через namespace).
   На Linux їхні пропускна здатність і ємність (64 KiB) збігаються; на macOS FIFO
   обмежений 8 KiB, тому там він помітно повільніший за анонімний `pipe`.
   Обидва — half-duplex, тому для ping-pong потрібні два канали.

4. **`socketpair(AF_UNIX)` vs `pipe`.** Сокет — повнодуплексний (один дескриптор
   для обох напрямків) і має більший буфер відправлення (233 KiB проти 64 KiB).
   Через це на великих повідомленнях (64 KiB) сокет обганяє `pipe` у ~5 разів:
   producer встигає «закинути» кілька повідомлень у буфер, поки consumer їх
   розбирає. На малих повідомленнях сокет, навпаки, повільніший за `pipe` через
   додаткові перевірки socket-рівня.

5. **`file` — найповільніший і найгірший для IPC.** Немає механізму сповіщення,
   тому consumer змушений постійно опитувати `fstat()` (busy-poll) — це видно з
   латентності (1 µs на Linux, 4.3 µs на macOS). Без `fsync` дані осідають у page
   cache, і швидкість ще прийнятна (88 MB/s на 64 B, 2.6–4.7 GB/s на великих
   блоках). Але `fsync` на кожне повідомлення обвалює пропускну здатність до
   **0.24 MB/s (~370× повільніше)** — це ціна гарантованої довговічності на диску.
   Висновок: файли — для обміну даними, а не для синхронізації процесів.

6. **`mqueue` — зручність проти швидкості.** Черга дає пріоритети, атомарність
   повідомлень і міжпроцесну адресацію без ручної синхронізації, але кожне
   повідомлення копіюється в ядро і назад, ємність жорстко обмежена
   (`mq_maxmsg × mq_msgsize`, типово 10 повідомлень), а розмір повідомлення
   обмежений `msgsize_max = 8 KiB`. Тому це найповільніший метод на малих
   повідомленнях (74.8 MB/s) і непридатний для великих блоків. Доречний для
   невеликих керуючих повідомлень із пріоритетами.

7. **Ємність визначає поведінку під навантаженням.** Мала ємність (mqueue: 40 KiB,
   pipe: 64 KiB) змушує producer блокуватися частіше → більше перемикань
   контексту. Велика (socket: 233 KiB, mmap: конфігурована) дозволяє згладити
   нерівномірність і підвищити пропускну здатність на великих блоках. Для
   потокового обміну великими обсягами слід збільшувати буфери (`SO_SNDBUF`,
   `F_SETPIPE_SZ`, `mq_maxmsg`, розмір кільця).

8. **Практичні рекомендації:**

   | Сценарій | Рекомендація |
   |---|---|
   | Мінімальна затримка, великі обсяги, споріднені процеси | `mmap_anon` + атомарне кільце |
   | Спільні дані між незалежними процесами | `shm_open` / `mmap_file` |
   | Потокова передача, простота, half-duplex | `pipe` |
   | Повнодуплексний обмін, інтеграція з сокетним API | `AF_UNIX` socket |
   | Керуючі повідомлення з пріоритетами | `mqueue` (Linux) |
   | Персистентність даних | файл (+ `fsync` за потреби) |
   | Міжмашинна взаємодія | TCP/UDP sockets (див. lab1) |

## 10. Обмеження дослідження

- Виміри в Docker/VM (colima) на Apple Silicon: абсолютні значення можуть
  відрізнятися від bare-metal Linux, але **відносні** співвідношення між методами
  зберігаються; це підтверджує окремий native-прогін на macOS.
- mmap-методи використовують busy-wait синхронізацію (spinning) — це навмисно:
  мета — виміряти межу латентності; у продакшені варто додати `futex`/`sem_wait`
  (дорожче на ~1–2 µs, але гуманніше до CPU).
- Throughput включає час запуску та планування дочірнього процесу; медіана з 3
  прогонів зменшує цей вплив.
- `file` без `fsync` вимірює page-cache шлях, а не довговічне зберігання.
